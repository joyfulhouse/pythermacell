## Findings and fixes

1. **Wrong device query parameter.** `ThermacellAPI` used `nodeid` for device
   params, status, config, and writes. The current app's Retrofit `ApiInterface`
   uses `node_id` for params GET/PUT and status. Requests now use `node_id`.
   Whether the server still accepts the old spelling is unverified; it is not
   safe to rely on it. A local aiohttp server asserts the exact query and body.
2. **Failure falsely reported as success.** Home Assistant ignored False results
   from all library controls, including off and refill reset. It could show off
   or a full cartridge after a rejected request. The coordinator now checks
   results and reverts optimistic state. Switch, light, and reset services
   surface failure as HomeAssistantError.
3. **Cloud acknowledgement was treated as physical completion.** The APK has a
   PowerStateCoordinator that reconciles the writable power flag with reported
   system state/status. Home Assistant now requests verified library power
   control. It polls at delays 0, 0.5, 1, 2, 4, 5 seconds, with a 20-second total
   confirmation deadline. Off requires the writable flag to be false and every
   reported System State/System Status to be 1. On requires true and an active
   state if a status is available. A mismatch returns failure; network errors
   propagate. Verification happens after the queued PUT, so the queue's
   10-second command deadline does not truncate the reconciliation schedule.
4. **Power parameter name assumed instead of discovered.** The app identifies
   power by `esp.param.power` and sends the config-provided name. The library
   now resolves a writable parameter of that type for both reading and writing,
   falling back to `Enable Repellers` for older/incomplete configs. It does not
   blindly send a second Power field.
5. **Active status hidden by a false control flag.** Home Assistant previously
   displayed Off whenever the writable flag was false, even if System Status
   was Protected. Known operational status now controls the polled switch and
   status display, exposing a hub that has not completed shutdown.
6. **Exceptions left optimistic values behind.** Library power, brightness,
   color, and refill updates reverted only on False results. They now restore
   prior values in finally blocks, including on exceptions and cancellation.
7. **Expired queue entries could execute later.** Commands whose waiting future
   has been cancelled/timed out are skipped before execution. Chained futures
   also handle cancellation without raising in their completion callback.
8. **LED brightness overwritten.** Home Assistant always sent LED-on after an
   explicit brightness/color command; LED-on sets brightness to 100. Explicit
   changes now retain their requested brightness.
9. **Refill support missing from the integration.** The library already exposed
   integer cartridge codes, but Home Assistant always used the 100-hour default.
   A per-hub, restored selector now supplies the reset code. Changing the local
   preference does not send a reset command.
10. **Bodyless success parsing and stale schema.** JSON-typed 204 responses no
    longer attempt JSON decoding. OpenAPI refill codes, runtime units, and unsafe
    LED Saturation write examples were corrected.

## Refill semantics

The Android `TriDeviceActivity.askForRefillResetValue` click handlers select
integer 0, 1, or 2; `setResetRefillValue` wraps that integer under the parameter
name and hub name, then submits it through DeviceParamUpdates.

| Value | Android label | Capacity |
| --- | --- | --- |
| 0 | Yellow Cap | 40 hours |
| 1 | Blue Cap | 100 hours (existing default) |
| 2 | Gray Cap | 180 hours |

`Refill Reset` is a cartridge-type reset command, not an incrementing counter
and not a generic boolean. The library now rejects bool/float inputs that Python
would otherwise consider equal to these integer codes.

Both projects read `Refill Life` directly from the hub/cloud. There is no local
elapsed-time depletion calculation. These fixes eliminate confirmed ways to
misreport a failed off or reset, but they do not prove why a particular hub
reported an empty cartridge after two hours. Firmware, stale cloud state, other
controllers, or a scheduled restart require live observations to distinguish.

## Hardware verification after installation

1. Select the installed cartridge capacity in Home Assistant. Reset only after
   replacing the cartridge, since reset discards the previous usage estimate.
2. Turn off through Home Assistant. Confirm that no service failure occurs and
   that the official app also reports Off. A confirmation failure must be
   investigated rather than treated as a completed shutdown.
3. Record Refill Life, System Runtime, the writable power flag, System Status,
   firmware version, and timestamps immediately and after 15 minutes and two
   hours. Refresh both clients before comparing.
4. If reported life continues decreasing while status is 1 and physical heating
   is stopped, capture those read-only snapshots for firmware/cloud diagnosis.
   Check app schedules and other automations for reactivation.
